# 非機能試験（負荷試験）の記録

- 実施日: 2026-10-09（日本時間 21:20〜22:20 ごろ）
- 実施者: Yoriyuki NAGATA（Claude Code が実行・集計）
- 対象の版: `c1eb8b9`（本番に反映済みの版。複数試合・空席・QRコード表示を含む）
- 結論: **6部屋 ×（閲覧30人＋出題者1人）を30分間続けても、エラーなし・応答は中央値28ms で、余裕を持って処理できた。** 処理能力の目安は、全試合の合計で閲覧者およそ300人。

## 1. 試験環境

| 項目 | 内容 |
|---|---|
| サーバー | AWS EC2 `t4g.micro`（arm64、2 vCPU、メモリ 906MB、ap-northeast-1）、gp3 12GB |
| CPU クレジット | unlimited（使い切っても止まらず、超過分は追加料金） |
| 構成 | CloudFront → nginx（コンテナ）→ scoreboard（uvicorn 1プロセス、コンテナ）。aql-sokuhou の app と同居 |
| URL | `https://aql-sokuhou.q-koken.com/score/…`（本番そのもの） |
| DB | SQLite（コンテナのボリューム） |
| 負荷をかける側 | 手元の PC（WSL2）から公開 URL へ。CloudFront・インターネット経由の応答時間を含む |

## 2. 試験方法

- 負荷は `tools/loadtest.py` で作った。ブラウザの動きをまねている。
  - **閲覧者**: 1人1接続。応答を受けてから1.5秒後に次の取得（`GET /api/games/<ID>/state`）をする。開始時刻はばらけさせた。
  - **出題者**: 1部屋に1人。入力画面の取得を1.5秒ごとに行い、判定（正解・誤答・スルー）を30秒ごとに送る。試合が終わって判定が断られた（409）ら、リセットして続ける。
- 試験のたびに本番に試験用の試合（`loadtest`、`lt-r1`〜`lt-r6`）を作り、試験後に削除した。
- サーバー側は、試験中に `tools/loadtest_sample.sh` でコンテナごとの CPU とメモリを約2秒ごとに記録した。あわせて CloudWatch の CPU と CPU クレジットを見た。
- CPU の % は `docker stats` の値で、**1コアを100%とする**（2コアで最大200%）。CloudWatch の CPU はインスタンス全体（2コアで100%）。

## 3. 結果

### 3.1 1部屋：閲覧20人＋出題者1人、5分間

| 項目 | 結果 |
|---|---|
| リクエスト | 4,122件（毎秒13.7件）。すべて成功 |
| 閲覧の応答時間 | 中央値 25ms、遅い方から5% 54ms、遅い方から1% 126ms、最大 3.1秒（1件） |
| 判定の送信 | 10件すべて成功。中央値 34ms |
| scoreboard の CPU | 平均5.5%、最大11.5% |
| メモリ | scoreboard 最大114MB |
| CPU クレジット | 減らなかった |

1リクエストあたりの CPU 時間は約4ms だった。

### 3.2 処理能力の限界：閲覧者を増やす（各60秒、1試合）

| 閲覧者 | リクエスト/秒 | エラー | 応答 中央値 / 遅い方から1% | scoreboard の CPU（平均 / 最大） | メモリ最大 |
|---|---|---|---|---|---|
| 20 | 13.7 | 0 | 25ms / 126ms | 5.5% / 11.5% | 114MB |
| 100 | 63.5 | 0 | 28ms / 163ms | 20% / 42% | 156MB |
| 300 | 179 | 0 | 36ms / 647ms | 56% / 98% | 187MB |
| 600 | 288 | **約9%**（502が1,236件、500が325件） | 327ms / 1,581ms | 93% / 136% | 399MB |

- 600人では、1プロセスで動く scoreboard の CPU がほぼ1コアを使い切った。その結果、応答が遅れ、エラーが出た。
- エラーの中身:
  - 500 は SQLite の `unable to open database file`（333件）。
  - 502 は、nginx がアプリから接続を切られたことによるもの（`Connection reset by peer`）。
  - リクエストが詰まって、開いているファイルや接続の数が上限（コンテナの `ulimit -n` は1024）に当たったと推測している。確証はない。
- 負荷を止めた後は、すぐに通常どおり応答した。
- 限界の試験の後、scoreboard のメモリは約235〜300MBのまま戻らなかった。コンテナを再起動すれば戻る。

## 4. 評価と運用上の目安

- **6部屋×30人（合計180人）は問題ない。** 応答は中央値30ms 前後で、30分間で悪くならない。限界の目安（約300人）の6割ほどの負荷。
- **処理能力の目安は、全試合の合計で閲覧者約300人（毎秒約180リクエスト）。** どの試合も1つのプロセスで処理するため、部屋の数ではなく閲覧者の合計で決まる。
- **CPU クレジット**: 合計180人の負荷では、満タン（288）から約12時間で使い切る。1日8時間の大会なら足りる。使い切っても止まらないが、超過分に少額の追加料金がかかる。
- **通信量**: 合計180人で約0.66GB/時（8時間で約5GB）。CloudFront の無料枠（毎月1TB・1,000万リクエスト）の範囲で、費用はほぼかからない。ただし8時間で約350万リクエストになるので、大会が月に3回を超えるとリクエスト数の無料枠に近づく。
- **限界を超えたとき**: 応答が遅れ、一部のリクエストが 500・502 になる。負荷が下がれば自然に戻る。閲覧画面は1.5秒ごとに取り直すので、エラーが散発しても次の取得で表示は戻る。

## 5. 300人を超える見込みがある場合の改善案（未実施）

1. 同じ版の閲覧用の応答を使い回し、DB の読み込みと JSON の組み立てを減らす。
2. 閲覧画面の取得の間隔を延ばす（1.5秒 → 3秒で、負荷はほぼ半分）。
3. 1リクエストで SQLite に3回接続している（`load`・`load_display`・`pw_hash_of`）のを1回にまとめ、確実に閉じる。
4. uvicorn のプロセスを増やす。ただし、ログインの失敗回数・署名鍵の保持・書き込みの排他を、プロセスをまたいで扱えるよう見直す必要がある。

## 6. 測定上の注意

- 負荷をかける側は手元の WSL2 で、ここは名前解決がときどき失敗する。そのため `tools/loadtest.py` では、一度解決できた結果を使い回している（CloudFront へ接続することに変わりはない）。
- 応答時間には、手元からのネットワークの往復（CloudFront まで）が含まれる。1秒を超えた少数の応答には、手元の回線や WSL の一時的な遅れも含まれる。
- EC2 上の `docker stats` による記録自体も CPU を使うので、インスタンス全体の CPU は実際の大会より少し高く出ている。

## 7. 再実行の手順

```bash
# 1) 管理者画面で試験用の試合を作る（例: lt-r1、パスワード PW）
# 2) EC2 で記録を始める（任意）
ssh aql-sokuhou-py "cat > /tmp/s.sh" < tools/loadtest_sample.sh
ssh aql-sokuhou-py "bash /tmp/s.sh 1870" > stats.txt &
# 3) 負荷をかける（部屋の数だけ並べる）
uv run python tools/loadtest.py https://aql-sokuhou.q-koken.com/score lt-r1 PW 30 1800 r1.json &
wait
# 4) 試験用の試合を管理者画面で削除する
```
